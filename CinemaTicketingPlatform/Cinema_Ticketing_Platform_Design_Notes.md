## 1. 项目概述

本项目为全栈开发的简易电影购票平台，模拟电影院的完整购票流程，包含：

- 消费者端：浏览电影场次、实时座位图选座、下单支付、订单与票务管理（待支付/待使用/历史购买）、转赠、退款申请
- 管理端：电影与场次管理、场馆（座位布局）管理、排片与冲突检测、座位安排、核销、退款审核

## 3. 技术栈讨论

### 3.1 Vue 与 React 的区别（讨论摘要）

| 维度 | React | Vue 3 |
|---|---|---|
| 写法 | JSX，HTML 写在 JS 里 | 模板 + SFC（HTML/JS/CSS 分块） |
| 状态响应 | 显式 setState + hooks，需理解重渲染 | 响应式代理，数据变更自动更新 |
| 官方配套 | 路由/状态管理靠社区选型 | 官方 Vue Router、Pinia |
| 学习曲线 | 偏陡，概念多 | 平缓，中文文档友好 |
| 生态 | 全球最大、库最丰富 | 国内生态强（Element Plus、Vant、uni-app） |
| 适用 | 大厂、国际化团队、灵活定制 | 中小项目、快速开发、国内团队 |

结论：两者都能完成本项目；图快速省心选 Vue，练主流技术栈选 React。最终选定 React。

### 3.2 最终技术栈（已确认）

| 层 | 选择 |
|---|---|
| 前端 | React + Vite + TypeScript |
| UI 组件 | Ant Design |
| 后端 | FastAPI（Python 3.12） |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic |
| 数据库 | MySQL 8.0（本机已运行） |
| 认证 | JWT（PyJWT + bcrypt） |
| 支付 | 支付宝沙箱（先 mock 实现，预留抽象层） |

选型理由：

- FastAPI 面向纯 API 后端，自动校验与文档，配合 React 前后端分离很顺
- SQLAlchemy 2.0 + Alembic 便于数据库迁移
- MySQL 已在本机安装并运行，无需额外折腾
- React + Ant Design 生态成熟，管理后台界面开发快

注意点：

- MySQL 8 默认 caching_sha2_password 认证，Python 连接需 PyMySQL + cryptography
- 前后端是两个独立项目，需分别启动（前端 npm run dev，后端 uvicorn）
- 部署时 React 构建为静态文件，FastAPI 用 uvicorn 运行，可同域名挂载

## 4. 需求讨论全过程

### 4.1 第一轮：初始需求

1. 模拟电影院购票，实时显示总票数。
2. 固定座位选座，实时展示场馆座位图（已售/待售直观展示，便于消费者看出座位分布与剩余情况）。
3. 已售座位点击时不显示座位信息，仅提示已售罄。
4. 防超卖：多人点击同一空位时，若他人已购买或已锁定未支付，则提示已售罄。
5. 座位释放：点击购买后直接付款即正式售出；点击购买未付款退出，为其保留 20 分钟，在消费者后台保留购买渠道，超时自动释放。
6. 支付方式：支付宝沙箱（后续申请）。
7. 管理后台：
   - 新建场馆（出入口位置、荧幕位置、座位排放等基础信息）；
   - 修改已有场馆；
   - 安排电影播放时间、占用场馆；
   - 对被安排电影的场馆进行具体座位安排（创建时确定最大容量，实际使用时具体安排）；
   - 冲突检测：场馆被安排后标记为使用中，避免排期冲突。

### 4.2 第二轮：补充规则

1. 定价：每个具体电影/场次由管理员在后台排片时具体设置。
2. 缓冲：电影时间确定后，其后 30 分钟内无法安排新内容（模拟观众离场与工作人员清理）。
3. 待支付上限：每个用户每次最多 3 张票（包括已购买未付款的）。
4. 核销：电影开始前 10 分钟后核销，标识已使用，无法退票；已使用的票转入历史记录。
5. 用户后台三个页签：待支付、待使用、历史购买（未支付自动释放的不计入历史）。
6. 转增：待使用中的票可通过用户 ID 转赠给另一个用户；票带标签标识是自己的还是别人转增的。
7. 退款：用户可申请退款，管理员决定；自购票可退，受赠票不可退；退款非原价，收取 10% 手续费。
8. 开售/停售：管理员设置开售时间与关闭时间；关闭时间一到，无论是否还有空余，锁定当前状态；已锁定未付款票自动释放，不为用户保留。

### 4.3 第三轮：细节确认（六条）

1. 核销语义确认：开场前 10 分钟，票无法转增、无法退掉；开场时有工作人员核销（模拟）。
2. 转赠：票只允许转增一次（受赠票不能再转）。
3. 退款后座位：释放并变为待售状态（售票期内；已停售则不上架）。
4. 票价粒度：场次统一票价（座位价格字段可预留，但分区定价不是本期重点）。
5. 三张上限口径：待支付 + 待使用 合计最多 3 张。
6. 转赠痕迹：原主人历史保留"已转赠"记录（含受赠人），受赠票带"受赠"标签。

### 4.4 第四轮：支付截止调整

- 支付截止默认 = 开场前 20 分钟（并与停售时间取更早者），防止时间线冲突。
- 核销入口、退款后座位处理按既定默认方案执行。

### 4.5 第五轮：最终确认与工程要求

1. 锁定期粒度：每张票有各自的锁定期（20 分钟），各自过期、各自释放，不按订单共享。
2. 退款粒度：按每张票处理（一张订单可只退其中某几张票）。
3. 排片冲突规则：已有订单的场次禁止删除或修改座位；只允许修改未来且未售票的场次。
4. 工程要求：项目需具备优秀全栈开发的特点——代码与架构、健壮性与异常处理、安全保障、性能与扩展性、文档与交付（详见 docs/工程规范.md）。

## 5. 定稿业务规则（完整版）

| 编号 | 规则 |
|---|---|
| R1 | 票价：场次统一票价，管理员排片时设置 |
| R2 | 缓冲：同场馆新场次开始时间须晚于旧场次结束时间 + 30 分钟 |
| R3 | 票数上限：每人待支付 + 待使用合计最多 3 张 |
| R4 | 锁座：每张票独立锁定 20 分钟，各自超时释放；停售到点强制释放 |
| R5 | 支付截止：默认开场前 20 分钟，且不晚于停售时间 |
| R6 | 冻结：开场前 10 分钟起，票不可转赠、不可退款 |
| R7 | 核销：开场时工作人员模拟核销，票转入历史购买 |
| R8 | 转赠：仅待使用、开场前 10 分钟前可转；仅可转一次；受赠票不能再转、不能退款 |
| R9 | 退款：按每张票处理；仅自购票、待使用、开场前 10 分钟前可申请；管理员审核；同意扣 10% 手续费、座位回待售；拒绝维持原状 |
| R10 | 开售/停售：管理员设置；停售到点锁定场次售卖状态，未付款票强制释放 |
| R11 | 冲突检测：同场馆时间区间（含 30 分钟缓冲）重叠即冲突；已有订单的场次禁止删除/改座位，仅未来未售票场次可改 |
| R12 | 已使用/已退款票转入历史购买；超时释放的不计入历史 |

## 7. 场次时间线（定稿）

1. 开售时间：开始售票，可选座下单。
2. 售票期：下单锁座 20 分钟，期间可支付。
3. 支付截止 = min(停售时间, 开场前 20 分钟)：到点所有未付款票强制释放，场次锁定售卖状态。
4. 开场前 10 分钟：票冻结，不可转赠、不可退款。
5. 开场：工作人员模拟核销，票转入历史购买。

锁定与释放均按票独立进行：同一订单中某张票到期，仅该票释放、座位回待售，其余票不受影响。

## 8. 核心实现方案（可行性结论）

### 8.1 防超卖：座位状态机 + 原子更新

座位三种状态：待售、锁定（待支付，20 分钟）、已售。抢座通过原子 SQL（UPDATE ... WHERE status=待售 并判断影响行数）或事务内 SELECT ... FOR UPDATE 实现，保证同一座位同时只有一人锁定成功。锁定期按座位/票独立记录（tickets.expires_at 与 session_seats.lock_expires_at），各自到期、各自释放。

### 8.2 超时释放：定时任务 + 惰性检查

定时任务按每张票/座位的过期时间扫描释放（分钟级）+ 查询时惰性判断（过期自动视为待售），双保险；释放同样使用原子更新，避免与购买并发冲突。

### 8.3 场馆与场次座位模型（模板复制方案）

- 场馆保存座位模板：行数、列数、屏幕位置、出入口、最大容量。
- 排片时复制模板生成该场次自己的座位表，管理员可微调（如关闭部分座位）。
- 好处：历史订单不受场馆布局修改影响；场次可独立定价与开放范围；数据量对 MySQL 无压力。

### 8.4 冲突检测

规则：同场馆、时间区间重叠（含 30 分钟清扫缓冲）即冲突。已有订单的场次不可删除、不可改座位；改动只影响未来场次。

### 8.5 实时性

先做轮询方案：加载时拉取 + 用户操作后刷新 + 每 5~10 秒自动刷新；后续可选 WebSocket 升级。

### 8.6 支付抽象层

先实现 mock 支付，支付宝沙箱接入只需替换实现类。注意沙箱异步回调需公网可访问地址，本地开发可用内网穿透（cpolar/ngrok）或以后端轮询订单状态为主。

### 8.7 用户后台与转赠/退款

用户后台三个页签（待支付/待使用/历史购买），含倒计时、转赠入口、退款申请入口；管理端含退款审核列表、核销入口（整场一键核销或按票核销，另设到点自动核销兜底）。

## 9. 已确认的实现默认值

1. 支付截止 = min(停售时间, 开场前 20 分钟)。
2. 核销入口：管理后台场次详情页提供整场一键核销与按票核销，并设到点自动核销兜底。
3. 退款后座位：售票期内回待售；已停售则不上架。
4. 锁定期按票独立：订单仅作聚合容器，支付按订单中仍处于锁定期内的票进行，金额同步更新。
